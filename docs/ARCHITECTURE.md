# 技术文档:SDK 内部机制

这份文档解释 SDK **为什么这么写**。读它的场景是:你要改 SDK、要移植到别的语言、
或者遇到了「签名被拒但看不出为什么」。

---

## 信任边界

```
主账号私钥                        API 钱包私钥
  ├ 入金 / 提款                     ├ 下单 / 撤单 / 换单
  ├ 授权 / 撤销 API 钱包            ├ 改杠杆
  └ 转账                            ├ 条件单 / TWAP
                                    └ 断线保护
  ↑ 冷处,只在授权时用一次           ↑ 放在跑策略的机器上
```

**这条线是在确定性状态机里强制的,不是网关的一层检查。**

内核里有一份显式白名单(`command_actor`),不在其中的命令一律 `AgentScopeViolation`。
白名单默认拒绝意味着:**新增命令不会自动获得 agent 权限**,必须显式列进去。

### 授权按 (账户, agent) 对记

一把 API 钱包可以被**多个账户各自**授权 —— 主账户与每个子账户分别同意,
状态机按对记账。由此:

- 撤销其中一个账户的授权,**不影响**这把 key 对其余账户的授权
- 没授权过的账户,这把 key 代不了它(`UnknownAgent`)—— 放宽不等于越权
- 泄漏一把 key 的爆炸半径,是**它被授权的那些账户**,不是整个 owner 名下

最后一条是刻意不跟 Hyperliquid 的地方:HL 是 owner 级放宽(一把 key 覆盖该
owner 的全部账户)。按对记账让每个子账户的授权都是一次显式同意 —— 而人们用
子账户,图的恰恰是风险隔离。能力上两者相同:想让一把 key 管三个子账户,
授权三次即可。

这个设计的代价是加命令时容易忘 —— 本 SDK 开发过程中就踩到了:新加的原子换单
首跑报 `AgentScopeViolation`,因为内核那边没列。代价换来的是「哪些操作能用 API key 做」
永远是一份看得见的清单,而不是「除了这几条以外都行」的隐式集合。

### 两个 nonce

| | 计数器 | 与什么绑定 |
|---|---|---|
| 授权/撤销 | **master 账户**的 | 账户生命周期 |
| agent 代执行 | **agent 地址**自己的 | 与授权项生命周期**解耦** |

第二条的解耦是刻意的:撤销后重新授权,agent 的 nonce **不重置**。否则旧签名在
重授之后会重新变得有效 —— 那是一个重放攻击面。

后果是:重授之后必须重读 `AgentNonce`,不能假设从 0 开始。

## 签名流水线

代执行的签名承诺的不是 JSON,是**内核规范编码的哈希**:

```
BatchOrder{...}
   │  EncodeBatchPlace()          ← dexos/codec.go,小端紧凑编码
   ▼
[]byte  01 31 03000000 …
   │  keccak256
   ▼
commandHash (32B)
   │  AgentExec(bytes32 commandHash,uint64 nonce) 的 structHash
   ▼
   │  keccak(0x19 0x01 ‖ domainSeparator ‖ structHash)
   ▼
signingHash (32B)
   │  secp256k1 可恢复签名 → r‖s‖v
   ▼
signature (65B)
```

服务端收到请求后:按 **JSON** 重建内层命令 → 用**自己的**编码器重编 → keccak → 比对。

所以有两条独立的路径描述同一条命令:

- **签名走编码**(你算的 `commandHash`)
- **传输走 JSON**(服务端据以重建)

两者必须描述同一条命令。改了 JSON 忘了改编码(或反过来)的表现是 **401**,
错误信息里没有任何指向根因的东西。

## 两种字节序,别混

同一个 SDK 里并存,这是最容易出错的地方:

| 用途 | 字节序 | 实现 |
|---|---|---|
| 规范命令编码 | **小端** | `encoder.u16/u32/u64`(内核用 `to_le_bytes`) |
| EIP-712 word | **大端**,32 字节右对齐 | `wordU32/wordU64/wordAddr` |

所以两套原语**刻意分开命名**,不共用辅助函数 —— 共用会让「这里该用哪个」变成
每次都要想一遍的事。

---

## 规范编码的具体布局

```
每条命令 = codecVersion(1B) ‖ tag(1B) ‖ 字段…
```

`codecVersion` 那个前缀字节是 SDK 开发时**第一个被金样抓出来的 bug** ——
比对结构体定义永远发现不了,因为 Rust 那边它在 `encode_command` 的函数体首行,
不在任何一条命令的分支里。

| 命令 | tag | 布局 |
|---|---|---|
| `CancelOrder` | `0x06` | account u32 ‖ OrderId u64 |
| `BatchCancel` | `0x0F` | account u32 ‖ len u32 ‖ OrderId u64 × n |
| `BatchPlace` | `0x31` | account u32 ‖ **nowMs u64** ‖ len u32 ‖ 订单 × n |
| `BatchReplace` | `0x3E` | account u32 ‖ nowMs u64 ‖ cancelsLen u32 ‖ OrderId × ‖ ordersLen u32 ‖ 订单 × |

订单项:`market u16 ‖ side u8 ‖ price u32 ‖ lots u64 ‖ tif u8 ‖ reduceOnly u8`

两个坑:

1. **`BatchPlace` 的 `nowMs` 在长度前缀之前**,而 `BatchCancel` 根本没有 `nowMs`
   —— 照着一个抄另一个必错。
2. **`BatchReplace` 有两个变长段挨在一起**,长度前缀写反顺序是最典型的错误。
   金样里专门有「只撤不挂」「只挂不撤」「空/空」三条边界钉这个。

`OrderId` 是打包值:`(market << 48) | seq`,编码时按 u64 整体写出。

`tag` **append-only**:内核那边只允许追加、禁止重排复用,所以这些常量一旦发布不能改。

## 金样对拍

规范编码是 SDK 唯一不能靠 review 保证正确的部分。所以有对拍:

```bash
# dex-os 侧生成
cargo run -q --example sdk_golden > ../dex-sdk-go/dexos/testdata/golden.json
# SDK 侧逐条重算并断言 hex 相等
go test ./dexos/
```

9 条金样覆盖:空集合、极值(`u32::MAX`/`u64::MAX`/`market 65535`)、
只撤不挂、只挂不撤、空/空。

测试还断言**双向完整**:金样里有而 Go 侧没有重算的条目会报错(内核加了命令而 SDK 没跟上),
Go 侧重算了而金样没覆盖的也会报错(有重算没被验证)。

移植到别的语言时,这份 `golden.json` 就是验收标准。

## 签名的 v 位序

`decred/dcrd` 的 `SignCompact` 产出 `v‖r‖s`,以太坊要的是 `r‖s‖v`。
`Signer.SignHash` 做了重排。

弄错的表现是「签名格式合法但恢复出别的地址」→ 服务端回 `UnboundSigner`,
而不是一个能指向根因的错误。这段值得单独看一眼,也是移植时最容易错的地方之一。

地址派生:`keccak256(未压缩公钥去掉 0x04 前缀)` 的后 20 字节。

## 事件流的并发模型

```
Subscribe() ──┬─→ Events chan(缓冲 1024)
              ├─→ Lost   chan(缓冲 1)
              └─→ Err    chan(缓冲 1)
```

连接同步建立，单个 goroutine 负责解析与分发：

- **Events 阻塞投递** —— 消费不过来就应该慢下来,丢事件比慢更糟
- **Lost** 最多报告一次服务端丢帧条数，随后 Err 报错并终止流
- 坏帧、缺字段、断线或 seq 倒退都显式终止；没有可靠历史补拉前不能继续做市

### seq 的语义

`seq` 是 **Raft 日志序号**,不是逐事件计数器:

- 同一条命令产出的多个事件**共享同一个 seq**(实测一条批量撤单的 22 条
  `OrderCanceled` 全是同一个值)
- 没有产生事件的日志条目会让它**跳号**

所以它只保证非递减。**丢帧检测不能用它** —— 跳号既可能是无事件的日志、
也可能是真丢了,不可区分。丢帧由服务端显式下发 `{"kind":"Lagged","dropped":n}`。

SDK 对 seq 只保留一条断言:**倒退即服务端 bug**(事件顺序不可信,比丢帧更严重)。

## 读一致性:为什么 REST 调用会带一个位号头

生产部署是**读写分层**的:写打 Raft voter,读打只读副本(learner)。
副本天然落后 leader,于是最朴素的用法会骗人 ——

```
下单 200 OK  →  立刻查持仓  →  落到还差一条日志的副本  →  「暂无委托」
```

**没有任何报错**,这是它最坏的地方。

所以 `Client.do` 在唯一的 HTTP 出入口处维护一条链:

- 成功响应里的 `x-dexos-seq`(写=这次写的提交位号,读=副本的已应用位号)
  并入 `Client.seq`(单调取大);
- 每个请求带上 `x-dexos-min-seq: <见过的最大值>`;
- 副本追不上就回 **412**,而不是返回旧值。

只在 **2xx** 上采信响应头是刻意的:412 的响应里带的是副本**本地**已应用位号,
把它当成"我见过的最大值"会让下一次请求要求得更松 —— 恰好是错的方向。

跨进程共用同一个账户时,用 `Client.Seq()` 把位号传给对方,
另一端 `Client.ObserveSeq(v)` 并入,两边的读就挂在同一条链上。

单成员部署上这两个头没有任何作用,零代价;老客户端不带头 = 老行为。
副本落后到超时的处置见 [`docs/API.md` 读一致性](API.md#读一致性read-your-writes)。

## 移植到别的语言要做什么

按工作量排序:

1. **规范编码**(`codec.go`)—— 小端 + 上表的布局。用 `golden.json` 验收。
2. **EIP-712**(`eip712.go`)—— keccak256 + 大端 word。域固定为
   `{name:"dex-os", version:"1", chainId:…, verifyingContract:0x0…0}`。
3. **可恢复签名**(`signer.go`)—— secp256k1,输出 `r‖s‖v`(v ∈ {27,28})。
4. REST / WS 客户端 —— 常规工作,无特殊之处,**但别漏掉位号链**:
   请求带 `x-dexos-min-seq`、2xx 响应并入 `x-dexos-seq`(单调取大)。
   漏掉它的移植版在单成员部署上一切正常,上了读写分层的生产就开始偶发读到旧值。

**验收分两层**,因为它们抓的错不同:

- 金样对拍证明编码正确 —— 静态,离线可跑
- 对着真节点跑证明签名路径正确 —— 域分隔符、v 位序、地址派生这三处错了,
  表现都是 401,静态检查看不出来

最后一步必须是**反证**:撤销授权后同一把钥匙再下单必须被拒。否则前面全绿也不能
说明授权真的起了作用。
